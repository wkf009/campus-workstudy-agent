## P0-安全与工程质量加固（进行中）

### P0-01【2026-08-27】接口越权修复 —— SecurityConfig 全放行

- **模块**：`config/SecurityConfig.java`、`filter/JwtFilter.java`
- **改动**：
  1. 删除 `anyRequest().permitAll()`，改为白名单 + 其余全部 `authenticated()`：
     - 匿名放行：`/api/auth/**`（登录注册）、`GET /api/departments`（首页/注册页部门下拉）、`/api/files/**`（图片直链）、Swagger/Knife4j 文档路径
     - 其余 `/api/**` 一律要求携带有效 JWT
  2. 自定义 401（未登录）/403（无权限）JSON 响应，替代 Spring Security 默认空响应
  3. `JwtFilter`：删除打印 JWT token 明文和参数的系统输出（**日志泄露 token 风险**），改为 SLF4J debug 级别
- **为什么改**：原配置所有接口匿名可访问，JWT 过滤器只解析 token 不拦截任何请求，等于没有鉴权。
- **面试怎么讲**：安全三原则——「默认拒绝、白名单放行、纵深防御」。URL 级粗粒度（必须登录）+ 方法级细粒度（角色）双层防护。
- **追问预案**：
  - Q：为什么用 URL 规则 + AOP 注解两套？A：URL 规则解决"是否登录"，注解解决"谁能调"，职责分离；且部分接口（如 `/admin/jobs/all`）多角色共用，URL 级写死角色会误伤，注解更灵活。
  - Q：401/403 返回格式？A：统一 JSON `{code,message}`，前端 axios 拦截器已按 401 跳登录、403 提示无权限。

### P0-02【2026-08-27】方法级角色鉴权 —— @RequireRole 注解 + AOP

- **模块**：新增 `aspect/RequireRole.java`、`aspect/RoleCheckAspect.java`、`common/AccessDeniedException.java`；修改 `common/GlobalExceptionHandler.java`
- **改动**：
  1. 新增 `@RequireRole({role...})` 方法注解 + AOP 切面：从 JWT 解析当前用户 → 查库校验角色 → 不匹配抛 `AccessDeniedException`（HTTP 200 + code 403，前端统一处理）
  2. 全局异常处理器捕获 `AccessDeniedException` 返回 403
  3. 给全部敏感接口标注角色：

| 接口 | 原状态 | 现要求 |
|---|---|---|
| POST /department/jobs（发布岗位） | 任意登录用户 | 角色 1/2（企业导师/部门管理员） |
| POST /admin/jobs/audit（岗位审批） | **任意登录用户可审批** | 角色 3（超管） |
| POST /admin/jobs/publish（发布操作） | **任意登录用户可调用** | 角色 3 |
| DELETE /department/jobs/{id}（删岗位） | 任意登录用户 | 角色 1/2 |
| POST /student/applications（提交申请） | 任意登录用户 | 角色 0（学生） |
| GET /student/applications/{userId} | **可查任意学生申请** | 仅本人或超管（所有者校验） |
| GET /department/applications（部门申请） | **学生也能看全部申请** | 角色 1/2/3，且 1/2 仅本部门 |
| POST /department/applications/process（审核申请） | **学生也能审核** | 角色 1/2 |
| GET/POST /admin/users*（用户管理） | 任意登录用户 | 角色 3 |
| /api/department/users/*（学生审批） | 任意登录用户 | 角色 2/3 + 部门归属校验 |
| POST/PUT/DELETE /departments（部门管理） | 任意登录用户 | POST/DELETE 角色 3；PUT 角色 2/3 + 只能改本部门 |
| GET /stats/*（统计） | 任意登录用户 | 角色 1/2/3 |
- **为什么改**：原代码权限全靠 Controller 手写且大量遗漏（`/admin/jobs/audit` 无任何校验），存在严重越权（学生可审批岗位、可审核申请）。
- **面试怎么讲**：注解式鉴权让"权限声明"和"业务代码"解耦；配合手写业务级校验（如部门归属）形成纵深防御。
- **追问预案**：
  - Q：为什么不用 Spring Security 的 @PreAuthorize？A：@PreAuthorize 需要开启方法安全且与 Spring Security 表达式耦合；自定义注解 + AOP 更贴合现有代码风格、可统一返回 Result 格式，也便于扩展（如将来加"数据权限"）。
  - Q：切面怎么拿当前用户？A：JWT 过滤器已把 userId 写入 request attribute，切面从 `JwtUtils.getUserIdFromRequest` 取，再查库拿角色（避免信任 token 里的角色声明被篡改——虽然 JWT 有签名，但查库是最稳的）。

### P0-07【2026-08-27】通知闭环 —— sendNotification 从"写了没人调"到全流程接入

- **模块**：`service/ApplicationService.java`、`service/JobService.java`、`mapper/JobMapper.java`、`mapper/ApplicationMapper.java`
- **改动**（通知类型：1-岗位通知，2-申请通知）：
  1. 学生提交申请 → 通知岗位发布人"收到新申请"（relatedId=申请ID）
  2. 部门审核申请（通过/拒绝）→ 通知学生审核结果 + 审核备注
  3. 超管审批岗位（通过/拒绝）→ 通知发布人审批结果 + 原因

  5. 两个 Mapper 的 `insert` 增加 `@Options(useGeneratedKeys)` 回填主键（原 `job.getId()` 插入后为 null 的隐患）

- **面试怎么讲**：功能闭环意识——"写好的能力必须被业务真正使用"；事务内通知保证一致性（同一事务，失败回滚）。
- **追问预案**：Q：通知和业务在同一事务，通知失败会回滚业务吗？A：会，这正是想要的强一致；如要解耦可用事务消息/发件箱模式（后续可演进）。

### P0-08【2026-08-27】文件上传白名单 + 目录穿越防护

- **模块**：`controller/FileController.java`
- **改动**：
  1. 上传后缀白名单（pdf/doc/docx/jpg/jpeg/png/gif/txt/md），拒绝可执行文件/脚本

### P0-09【2026-08-27】学生岗位列表服务端分页 + 搜索/筛选下沉 SQL

- **模块**：`mapper/JobMapper.java`、`service/JobService.java`、`controller/JobController.java`、`frontend/src/components/StudentJobs.vue`
- **改动**：
  1. `GET /student/jobs` 支持 `page`/`pageSize`/`keyword`/`departmentId` 参数，返回 `PageResult{records,total,page,pageSize}`
  2. 排序（本部门优先 + 薪资降序）、关键词搜索（标题/描述 LIKE）、部门筛选全部下沉到 SQL，配合 **PageHelper** 分页
  3. `JobService.getPublishedJobsPage`：`finally` 中 `PageHelper.clearPage()` 防御性清理 ThreadLocal
  4. 前端 `StudentJobs.vue`：列表改用分页接口 + `a-pagination` 分页器，搜索/筛选改为服务端查询（原为前端内存过滤，分页后会只过滤当前页）
- **为什么改**：原列表一次拉全量、前端内存过滤；数据量上来后不可持续，且分页后内存过滤语义错误。
- **面试怎么讲**：分页三要素——SQL 层排序保证分页语义正确、PageHelper 拦截器自动拼 LIMIT 与 count、`clearPage()` 防 ThreadLocal 泄漏；"排序/筛选/分页在数据库做"是性能基本盘。
- **追问预案**：Q：为什么不用前端分页？A：全量拉取随数据量增长不可扩展；服务端分页 + count 查询是标准做法。Q：PageHelper 原理？A：MyBatis 拦截器在执行前改写 SQL 追加 LIMIT，并执行 count 查询填充 total。
