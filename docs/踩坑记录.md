# 踩坑记录（面试素材：真实问题排查史）

> 记录本项目开发中遇到的每个坑：现象 → 原因 → 解决 → 启示。
> 面试官问"你遇到过什么难解决的问题"时，从这份文档里挑。
> 更新规则：每个阶段（P/M）实施时遇到的新坑实时追加。

## 历史坑（P0-P4 阶段）

### K-01【P0-05】MySQL 8 认证报错 Public Key Retrieval is not allowed
- **现象**：Spring Boot 3.4 升级后启动失败，`SQLNonTransientConnectionException: Public Key Retrieval is not allowed`
- **原因**：Boot 3.4 自带 mysql-connector-j 9.1.0，MySQL 8 的 `caching_sha2_password` 认证要求 JDBC URL 显式允许公钥获取
- **解决**：JDBC URL 追加 `&allowPublicKeyRetrieval=true`（dev + docker-compose 同步改）
- **启示**：升级依赖要关注"隐式行为变化"，不是只改版本号

### K-02【P1-01】spring-ai-alibaba BOM 里没有 spring-ai-alibaba-starter
- **现象**：Maven 报 `dependencies.dependency.version ... is missing`，编译失败
- **原因**：BOM 实际管理的 artifactId 是 `spring-ai-alibaba-starter-dashscope`（细粒度 starter），不存在全量 `-starter`
- **解决**：改依赖为 `spring-ai-alibaba-starter-dashscope`
- **启示**：用 BOM 前先 `mvn dependency:tree` 或直接看 BOM 的 pom 确认 artifactId，别想当然

### K-03【P1-01】Spring AI 1.0 SearchRequest 没有 query(String) 静态方法
- **现象**：`SearchRequest.query(text)` 编译报错"找不到符号"
- **原因**：Spring AI 1.0 的 SearchRequest 用 builder 模式（`SearchRequest.builder().query().topK().build()`），没有 query 静态工厂
- **解决**：改用 builder
- **启示**：AI 框架 API 迭代快，先查依赖树里的版本再写调用代码

### K-04【P0-02】已暂存的文件不受 .gitignore 影响
- **现象**：`git add -A` 后 Vite 临时文件 `*.timestamp-*.mjs` 仍被暂存，且 `git check-ignore` 返回不匹配
- **原因**：文件已进暂存区后，忽略规则不再生效（check-ignore 对已跟踪路径不报）
- **解决**：`git reset` 清空暂存 → 更新 .gitignore → 重新 `git add -A`
- **启示**：提交前先确认 ignore 生效；clean 的首次提交很重要

### K-05【P0-02】PowerShell 不支持 `<` 重定向 / cmd 引号转义地狱
- **现象**：`mysql < init.sql` 报"此处不允许使用重定向运算符"；`cmd /c "..."` 多层引号解析错乱
- **原因**：PowerShell 没有类 Unix 的 `<` 输入重定向；cmd 字符串在 PowerShell 里嵌套转义复杂
- **解决**：用 mysql 的 `source` 命令执行 SQL 文件（注意**中文路径 source 会失败，先复制到 %TEMP% 无中文路径**）
- **启示**：Windows 下跑数据库脚本优先 `mysql -e "source <无中文路径>"`

### K-06【P2-01】测试里 DashScope 无 Key 时上下文加载失败
- **现象**：API Key 移出配置后，`@SpringBootTest` 报 `DashScope API key must be set`
- **原因**：dashscope 自动配置在 key 为空时创建 ChatModel/EmbeddingModel bean 抛异常 → 整个上下文启动失败
- **解决**：测试类加 `@SpringBootTest(properties = "spring.ai.dashscope.api-key=test-api-key")` 占位 key
- **启示**：LLM 组件的 bean 创建是"硬依赖"，测试与无 Key 环境要显式给占位配置

### K-07【P2-01】启动时全量向量索引拖垮测试（147s）
- **现象**：新增启动索引 ApplicationRunner 后，AuthControllerTest 耗时 147s（重试 10 次 401）
- **原因**：Spring AI Retry 默认 max-attempts=10，无效 Key 时启动索引反复重试
- **解决**：**删掉启动索引，改为首次推荐时懒加载**（isEmpty() 判断）——启动零 LLM 调用，架构更优
- **启示**：启动期不要做依赖外部服务的重试型工作；懒加载往往更优雅

### K-08【P2-01】Spring AI 的 UserMessage 包路径变化
- **现象**：`import org.springframework.ai.chat.prompt.UserMessage` 编译失败
- **原因**：Spring AI 1.0 中消息类在 `org.springframework.ai.chat.messages` 包（不是 prompt 包）
- **解决**：改 import 到 `org.springframework.ai.chat.messages.*`
- **启示**：AI SDK 包结构变动频繁，报错先看正确包路径

## 多 Agent 协作阶段（M1-M7，持续追加）

### K-09【M2】Agent 同步调用进业务请求链路导致接口超时
- **现象**：发布岗位接口 15s 超时（客户端断开），但服务端实际完成了"预审+修订循环"（岗位已插入、agent_task SUCCESS、修订后 PASS）
- **原因**：`submitJob` 在事务内同步调用 `CoordinatorAgent.onJobSubmitted` → LLM 预审（可能多轮修订）耗时 20-40s，阻塞 HTTP 响应
- **解决**：事件驱动异步化——`submitJob` 发布 `JobSubmittedEvent`，`@TransactionalEventListener(AFTER_COMMIT)` + `@Async` 在事务提交后独立线程执行预审/修订；发布接口秒回
- **启示**：**LLM 调用永远不要同步阻塞在用户请求链路上**（除非明确需要同步结果）；异步 + 事件驱动 + 任务留痕（agent_task）是 Agent 集成的标准姿势。M1 时已预见到这个权衡，M2 实测验证了必须异步
- **面试话术**：为什么用 AFTER_COMMIT 而不是直接 @Async？A：@Async 线程可能在事务提交前就查岗位（查不到）；AFTER_COMMIT 保证数据可见后再跑
